# Independent PR #11 benchmark harness review

Read `tools/bench.ts` and `tools/lib/bench-measure.ts` before reading their tests. Then inspected stats contracts, docs, `test/bench-measure.test.ts` and `test/bench-cli.test.ts` to assess coverage. Read-only: no tests, calibration runs, production mutations or implementation edits. Root's forced single-pair control is independent of this review.

## Findings

1. **Recorded second-round layout shifts cannot fail the gate** (`tools/bench.ts:148–151`). The first round flags timing candidates; those scenarios are measured again and all second-round samples are persisted. However, layout-shift reporting/failure reads only `first.get(id)`. A run with first-round HEAD shifts all zero, a first-round timing flag that does not reproduce, and a second-round HEAD shift >0 exits successfully and prints zero worst shift. This violates the stated "HEAD's must be 0" and "worst opening" contract for recorded samples. Aggregate shifts over first and second rounds (when present) for both display and decision. Cheap independent property: appending a positive HEAD shift in any recorded round must cause layout failure regardless of timing verdict; adding a zero-only round changes nothing. No additional real-browser timing trials are needed to prove that decision law.
2. **A close failure skips remaining resource cleanup** (`tools/bench.ts:162–170`). `await browser?.close()` precedes server closure and worktree removal. If it rejects, later cleanup is not attempted; a throwing server close similarly bypasses worktree cleanup. This is a bounded error-path problem in a resource-owning CLI. Nest cleanup in finally blocks or attempt all closures while retaining the original failure. No normal-path regression is established; the existing measure context cleanup is correctly in finally. A browser launch/new-context/new-page or navigation failure should still release whichever earlier resources exist.

No other concrete correctness defect was established by inspection. The remaining items below distinguish verified design from untested contracts, rather than presenting hypothetical failures as discovered bugs.

## Protocol/lifecycle assessment

- Init recording is installed before navigation; performance timestamps and input event timestamps share Chromium's monotonic document clock. Ready comes from the actual data-ready marker, step completion from rayner:step, and first motion from a mutation under the stage rather than the earlier stage label update.
- Protocol requires at least three distinct nonempty named steps; the middle Next and last-step jump therefore target different unvisited names. The measured resting event must be at/after its click, and stage mutation must lie within the actual Next interval. Missing mutation rejects rather than manufacturing a zero timing.
- Final read waits two rendering opportunities and a task turn, then drains both performance observers with takeRecords. This is meaningful protection against pending longtask/layout-shift delivery. The real browser keeper proves longtask/blocking/stage/rest/gap behavior at readMs=0; it does not separately isolate a late observer delivery or positive shift.
- readMs=0 reaches the actual waitForTimeout(0) path, not an `||` default that would replace it with 1000. READ_MS remains an unused old constant in the CLI, but actual measurement uses validated `readMs`; this is clarity cleanup, not a behavior defect.
- All computed sample fields must be finite and nonnegative. Stats helpers reject invalid window bounds, task/frame data and nonchronological frames. Raw page-log cardinality/missing-step failures currently surface through tuple destructuring/non-null assertions, potentially as a TypeError; they fail closed, but explicit protocol diagnostics would make investigations clearer. Do not claim these bad-data rejection paths are directly covered by the one happy fixture.
- Browser pageerror during observation rejects the opening. Network/console errors are not separately rejected; this is narrower than the product's offline/no-console-error owners, which remain the right place for those independent contracts.

## Orchestration and provenance assessment

- BASE runs npm ci inside its detached temporary worktree, avoiding dependency symlinks and honoring its own package-lock. Both sides run their own source CLI builds, with current Node; this supports dependency-changing baselines. HEAD uses existing installed dependencies, so lock hashes record intended inputs but do not themselves prove HEAD node_modules matches the lock. Document the standard install precondition or verify it when stronger provenance is required.
- Artifact identity hashes complete built HTML plus header recipe. Exact identity avoids timing indistinguishable artifacts and writes an explicit "no browser timing claim" outcome. --force intentionally bypasses this shortcut. A successful identity skip is different from a measured timing pass; output says so.
- Every measured scenario on both sides gets an unrecorded opening before interleaved pairs; warmup is not confined to the first selected scenario. Alternating side order and per-opening contexts remain. Recordings retry only scenarios with flagged timing metrics, and timing failure requires a repeated regression. Thresholds are explicitly called heuristic rather than universally calibrated.
- Positive safe reps, finite cpu>=1 and finite readMs>=0 are validated before expensive dynamic imports/builds; catalog entries must be distinct. Fewer than MIN_PAIRS measured pairs cannot establish a timing pass and produce exit 2 unless a layout regression already requires exit 1. Identity shortcut may exit 0 at low reps because no timing claim is made; this is coherent with its separate outcome.
- Metadata records immutable base/head commits, tracked dirty state, Node/npm, per-side package/lock digests, artifact digests, reps/cpu/readMs/viewport/rules, identity/force status, working diff hash, untracked path/content hashes, browser version and raw rounds. This is materially stronger evidence than console medians alone. Host OS/architecture/CPU model and explicit sample outcome could improve archival context, but their absence does not invalidate within-run pairing.
- Samples are saved before reporting/exit judgment. Worktree add, npm/build/launch/measure/write failures enter outer cleanup; resource-close failures themselves have the specific cleanup gap above.

## Coverage after independent analysis

`test/bench-measure.test.ts` retains a real Chromium transport/lifecycle fixture, readMs=0, forced >100ms click blocking, actual stage writes and resting events. It asserts load readiness, mutation latency, rest ordering, frame gap, clipped blocking bound and zero shifts. Keep it: arithmetic properties cannot prove observer installation/delivery or DOM event timing.

`test/bench-cli.test.ts` covers malformed reps/cpu/read-ms and duplicate/invalid catalog entries through subprocess exit before build. It does not cover the valid identity shortcut, warm-all behavior, insufficient measured-pair exit 2, cleanup failures, or second-round layout decisions. Root's real forced single-pair control can substantiate one CLI path, not every orchestration law.

Prioritize a cheap decision oracle for all recorded layout shifts and bounded cleanup proof, plus focused protocol rejects for too few/duplicate names and absent stage mutation if adding further coverage. Keep the existing pure stats properties for numeric decisions; do not replace the actual observer integration with many synthetic timing fixtures. No test additions or source changes were made by this reviewer.
