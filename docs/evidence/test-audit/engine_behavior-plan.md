## Scale, mutation and validation

A useful separately labelled scale probe is a large common prefix/suffix (for example 100,000 lines) with a tiny changed middle in diffLines: assert exact reconstructed meaning and completion without stack overflow. Its purpose is to exercise documented head/tail trimming. Huge all-different sides invoke quadratic LCS work; huge identical-key assignment invokes cubic Hungarian work. Neither is an appropriate routine generated case or a basis for arbitrary timeout assertions.

Targeted mutation candidates: ignore Circumscribe.fadeOut; eagerly construct ViewSync targets; omit caption hold or rounding; merge a wrong description overwrite order; return nonoptimal repeated-key assignment; lose an inserted/deleted token; ignore heading:false; retain a stale Code.lines alias; skip later Succession updater initialization. Each must map to a named value/lifecycle keeper before claiming preservation. Agreement of two executions sharing the mutated implementation is insufficient on its own.

After edits, run focused affected files with the repository's existing test runner, then required `npm run check` and the configured full/CI checks once changes stabilize. Validate changed timing helpers leave an explicit real-play comparison. Have a separate adversarial reviewer read implementation/contracts without first seeing tests, as required by the audit workflow; root owns that later review. No mutation results or new test passes are claimed in this discovery artifact.
