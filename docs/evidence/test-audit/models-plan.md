## Corrected CIDR hypothesis and confirmed malformed-range defect

The initial read-only hypothesis classified `/0` rejection as a defect from standard CIDR notation. Pinned-source validation disproved that hypothesis for the model's named proxy-addr contract. `proxy-addr` v2.0.8 `package.json:20` pins ipaddr.js1.9.1. `index.js:31` defines `DIGIT_REGEXP = /^[0-9]+$/`; `parseipNotation` at :153–195 accepts a decimal prefix then rejects range<=0 or >32. Thus `/0` remains rejected. ipaddr.js1.9.1 `lib/ipaddr.js:531–547` has a *different* parseCIDR API that accepts0..32; conflating the two APIs caused the mistaken hypothesis. The final test classifies the full generated0..32 input:0 must reject;1..32 use independent network arithmetic. Production documentation now states1–32 and distinguishes boolean false membership from the upstream configuration parser's TypeError.

Pinned sources fetched for inspection (not installed as dependencies):

- https://raw.githubusercontent.com/jshttp/proxy-addr/v2.0.8/package.json
- https://raw.githubusercontent.com/jshttp/proxy-addr/v2.0.8/index.js
- https://raw.githubusercontent.com/whitequark/ipaddr.js/v1.9.1/lib/ipaddr.js

Original bounded probe returned `/0 false`, `/8.5 true`, `/8e0 true`, empty-prefix false and `/33 false`. `/0` was correct; fractions/exponents were wrong under the pinned decimal-digit grammar. Extra slash components were also incorrectly discarded by destructuring. The repair requires the whole range string to match an IPv4 address with at most one decimal-digit prefix and retains range1..32. Empty prefix, whitespace, fractions, exponent/sign/junk suffix, multiple slash, missing/out-of-range octet all reject. The new malformed property naturally failed on the original implementation at seed1701/path0:0:0:0:0:1:0, shrunk counterexample `["0.0.0.0", "1.5"]`; see models-cidr-red.tap. Final focused controls preserve all frozen real Express answers. This is a real model fix to land separately from test cleanup; no `/0` domain expansion was made.

Hop-count/list properties (`test/explain-trust-proxy.test.ts:131,150`) currently call production `forwarded` to derive expected addresses; the list oracle also calls `inRange`. Build expected address order directly from input socket plus reversed generated nonempty header fields, and use arithmetic network membership. Otherwise two helpers with the same ordering/mask bug can agree. Generate `reqIps` independently as the reversed retained prefix without the socket; keep no-header, n=0, n>=chain length and first-untrusted boundaries.
